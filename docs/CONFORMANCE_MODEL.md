# 🧪 Conformance and Shadow-Evidence Model

> **Status:** `ACCEPTED ABSTRACT CONTRACT / C4 IMPLEMENTED PARTIALLY / NOT A CERTIFICATION PROGRAM`  
> **Purpose:** define how present or future profiles demonstrate bounded Native Kernel contract support, cross-profile equivalence and non-authoritative offline shadow evidence

## 1. Why conformance matters

Technology independence must be tested, not merely declared.

```text
same accepted contracts
        ↓
materially different profile A
materially different profile B
        ↓
declared comparable behaviour
        ↓
assertion-scoped evidence
        ↓
approved offline recorded observations
```

Conformance concerns meaning and observable behaviour. Identical code or storage layout is not required. Identical bytes are required only where an assertion or equivalence class declares byte equality.

C4 is an evidence layer over C3. It does not create a new authoritative profile or deployment mode.

## 2. Conformance levels

| Level | Meaning | Required evidence |
|---|---|---|
| **C0 — Described** | A profile maps itself to a contract | architecture mapping |
| **C1 — Locally exercised** | Behaviour runs in a recorded local environment | commands, tests and failures |
| **C2 — Repository reproduced** | A third party can reproduce one profile’s supported assertion | committed code, CI, environment, traceability and artifact |
| **C3 — Cross-profile equivalent** | Two materially different profiles preserve a declared equivalence | shared fixtures, independent implementations and comparison artifact |
| **C4 — Shadow evaluated** | Approved immutable recorded workloads are compared without authority promotion | exact dataset, metrics, failures, Receipts, repository artifact and authority boundary |
| **C5 — Operationally validated** | A bounded deployment has security/privacy/rollback/incident evidence | explicit operational review |

Levels are assertion-scoped and independent from decision status, implementation status, evidence level, support state and operator approval.

```text
support_state: PARTIAL
kernel_runtime_conformance: C4
```

is valid when C4 applies only to results marked `SUPPORTED` and other results remain `PARTIAL` or `UNSUPPORTED`.

## 4. Assertion result states

Every registered assertion appears exactly once as:

| State | Meaning |
|---|---|
| `SUPPORTED` | declared bounded behaviour was directly reproduced |
| `PARTIAL` | meaningful behaviour was reproduced but an explicit gap remains |
| `UNSUPPORTED` | sufficient support is absent or the assertion is not accepted |
| `FAILED` | a required declared check executed and failed |

Unsupported assertions remain visible. `FAILED` cannot be silently converted to `UNSUPPORTED`.

## 5. Single-profile C2 protocol

`nk-evidence-report/1` contains:

- profile ID;
- support state;
- assertion-scoped level;
- evidence level;
- all 72 results;
- executed checks;
- report-wide limitations.

Every `SUPPORTED` or `PARTIAL` result references passed checks in the same report and states limitations.

The generic runner invokes an adapter:

```bash
python tools/conformance/runner.py adapter \
  --output report.json \
  -- <adapter-command>
```

It rejects malformed JSON, missing/duplicate/unknown assertion IDs and invalid statuses. Profile-specific validators additionally guard exact maps, traceability, proposed-family non-promotion and repository metadata.

## 6. Cross-profile C3 protocol

`nk-equivalence-report/1` is generated by the dedicated comparator rather than the single-profile evidence runner:

```bash
python tools/conformance/cross_profile_comparator.py \
  contracts/fixture-pack.json \
  > c3-equivalence-report.json

python tools/conformance/validate_p5_report.py c3 \
  c3-equivalence-report.json --require-repository
```

The comparison report contains:

- comparison/profile IDs;
- exact commit/run/Python/PostgreSQL/SQLite environment;
- declared equivalence classes;
- allowed and forbidden differences;
- passed cross-profile checks;
- all 72 assertion results;
- support counts and limitations.

The strict validator rejects wrong protocol/profile/support state, missing IDs, wrong `45/10/17/0` map, unsupported promotions, unknown checks, missing limitations and false repository metadata.

## 7. C4 offline shadow protocol

C4 requires two inputs:

```text
1. exact approved nk-shadow-workload/1 dataset bytes
2. exact validated nk-equivalence-report/1 prerequisite
```

Generation and validation:

```bash
python tools/conformance/offline_shadow_evaluator.py \
  contracts/shadow-workload-v1.json \
  artifacts/c3-equivalence-report.json \
  > artifacts/c4-shadow-report.json

python tools/conformance/validate_c4_report.py \
  artifacts/c4-shadow-report.json --require-repository
```

`nk-shadow-report/1` contains:

- exact dataset ID, protocol and SHA-256;
- exact C3 prerequisite digest;
- authority boundary;
- threshold policy;
- environment metadata;
- one result per recorded case;
- one bounded `nk-shadow-receipt/1` per case;
- semantic, critical, coverage and Receipt metrics;
- declared allowed operational differences;
- all 72 assertion results;
- report-wide limitations.

The evaluator is fail-closed. Critical semantic divergence, missing Receipts, incomplete C3-supported coverage, unsafe authority fields, changed protocol/digest or invalid metadata produces failure rather than promotion.

## 8. C4 authority boundary

C4 is valid only when:

```text
mode:                  SHADOW_ONLY
authority promotion:   FORBIDDEN
authoritative writes:  FORBIDDEN
side effects:           FORBIDDEN
promotion decision:    NOT_AUTHORIZED
```

The evaluator must not:

- append Events;
- mutate authoritative history or projections;
- grant/revoke authority;
- invoke external tools or actions;
- approve or activate a candidate;
- wire itself into Titan, Mentaury or Crystal.

```text
shadow observation
≠ command admission
≠ authority promotion
≠ production deployment
```

## 11. C3 equivalence classes

| Class | Required comparison |
|---|---|
| **BYTE** | identical canonical identity vectors and exact imported Event bytes/hash chain |
| **STRUCTURAL** | equivalent required report/contract fields and relations |
| **SEMANTIC** | preserved reducer state, projection state and Receipt proof boundaries |
| **BEHAVIOURAL** | equivalent accepted/rejected commands, idempotency, fencing and order |

### Allowed C3 differences

- SQL dialect and schema/index layout;
- server topology versus a single local file;
- PostgreSQL row locks versus SQLite `BEGIN IMMEDIATE`;
- independently generated Event IDs and timestamps;
- IAM, networking, replication, failover, concurrency and administration;
- non-semantic metadata and query plans.

### Forbidden C3 differences

- canonical identity and Command digest;
- payload meaning and declared order;
- hash-chain validity;
- reducer/projection canonical state;
- idempotency, stale-writer and corruption outcomes;
- Receipt proof booleans and limitations;
- exact bytes/hash commitments during authoritative-history import.

## 13. C4 comparison fields and thresholds

Recorded observations cover canonical identity, authority denial, writer fencing, idempotency, ordering, Event integrity, replay, projection rebuild, source/conflict binding, failure semantics, state equivalence, Receipt proof boundaries, exact history import and report traceability.

Thresholds:

```text
critical divergences max:     0
semantic divergence rate max: 0.0
missing Receipts max:         0
C3-supported coverage min:    1.0
latency ratio max:             2.0 (informational operational field)
```

Allowed operational differences are explicit and excluded only from semantic matching when declared. Normalization must never hide identity, payload, order, state, outcome, integrity or proof-boundary differences.

## 14. Shadow Receipt boundary

Each `nk-shadow-receipt/1` binds:

- case ID;
- dataset digest;
- comparison digest;
- assertion scope;
- matched/divergence outcome;
- `OBSERVE_ONLY` decision;
- absence of authority promotion, writes and side effects;
- explicit non-proofs.

A Shadow Receipt proves only that one declared recorded case was compared under the stated inputs and limits.

```text
Shadow Receipt
≠ truth certificate
≠ authenticity signature
≠ deletion proof
≠ production-safety approval
```

## 17. Artifact boundary

Artifacts have finite retention. A digest without retained bytes is not sufficient reproduction evidence. Future contract, profile, dataset, threshold or evaluator changes require new reports and artifacts.

Long-term evidence retention remains affected by Issue #18/publication decisions.

## 18. Non-conformance examples

```text
❌ Unsupported assertions are omitted.
❌ A top-level C2/C3/C4 label is described as support for all 72.
❌ Environment matrix jobs are described as independent profiles.
❌ C3 semantic equivalence is described as operational equivalence.
❌ Offline recorded data is described as live production shadowing.
❌ A matched shadow case is described as authority promotion or candidate approval.
❌ Dataset observations or thresholds change without a new version/digest/evidence cycle.
❌ Allowed-difference normalization hides payload/order/state/outcome/Receipt differences.
❌ A Shadow Receipt is described as truth, authenticity, deletion or safety certification.
❌ Proposed NK-EPI fixtures are described as accepted semantics.
❌ Clean P1–P5/C4 work is described as recovered v0.1.2.1 evidence.
❌ Operator approval is presented as empirical proof.
```
